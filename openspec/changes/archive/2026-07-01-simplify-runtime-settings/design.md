## Context

Сейчас `Settings` собирает runtime-конфиг из `.env` и TOML, но публичный контракт содержит много полей, которые на практике являются стабильными repo defaults: путь к `settings.toml`, путь к SQLite, директория промтов, `topics.md`, директория persona-файлов, а также ряд Gemini retry/timeout параметров. Эти значения разрастают `config/settings.toml`, `.env.example` и setup-документацию, хотя редко меняются на уровне конкретного swarm-инстанса.

При этом change затрагивает несколько слоёв сразу: `core/config.py`, runtime bootstrap в `run.py`, тесты конфигурации и документацию. Также затрагивается OpenSpec capability `runtime-configuration`, потому что меняется сам публичный конфиг-контракт.

## Goals / Non-Goals

**Goals:**
- Сделать `config/settings.toml` короче и сосредоточить его на действительно инстанс-зависимых настройках.
- Убрать `SETTINGS_PATH` из стандартного bootstrap-потока и использовать `config/settings.toml` как встроенный путь по умолчанию.
- Перенести стабильные repo paths и технические runtime defaults в код, сохранив совместимость runtime-поведения.
- Обновить примеры, документацию и тесты так, чтобы минимальный конфиг для нового инстанса был очевиден.

**Non-Goals:**
- Не менять swarm runtime, scheduler semantics, group routing или формат persisted SQLite данных.
- Не вводить новый формат конфигурации помимо текущего TOML + `.env`.
- Не делать крупную миграцию prompt-архитектуры или Gemini client API.
- Не удалять существующие runtime-поля `group_chat_id`/`group_target`, если они используются как legacy overrides вне публичного примера.

## Decisions

### 1. `config/settings.toml` становится встроенным default path

`Settings` будет искать TOML по умолчанию в `config/settings.toml`, без обязательного `SETTINGS_PATH` в `.env`. Явный override пути остаётся только как внутренний/тестовый механизм через конструктор `Settings(settings_path=...)` и, при необходимости, через process env для совместимости тестов/локальных сценариев.

Почему так:
- путь стабилен на уровне репозитория;
- это убирает лишнюю переменную из `.env.example`;
- пользовательский bootstrap становится проще.

Альтернативы:
- Оставить `SETTINGS_PATH` как основной documented path. Отклонено: не даёт пользы в типовом сценарии.
- Жёстко запретить любой override пути. Отклонено: ухудшает тестируемость и локальные спец-сценарии.

### 2. Repo-managed paths уходят из публичного TOML-контракта

Секции `[storage]` и `[prompts]` перестают быть частью минимального пользовательского конфига. Код использует встроенные defaults:
- `db_path = "data/history.db"`
- `prompts_dir = "ai/prompts"`
- `topics_path = "ai/prompts/topics.md"`
- `bot_profiles_dir = "ai/prompts/bots"`

Почему так:
- это свойства структуры репозитория, а не настройки инстанса;
- они уже предполагаются в документации и тестах как “обычные” значения;
- меньший контракт проще поддерживать.

Альтернативы:
- Оставить `[storage]` и `[prompts]` как есть. Отклонено: сохраняет лишний шум.
- Убрать только `[prompts]`, но оставить `[storage]`. Отклонено: даёт половинчатое упрощение при той же сложности docs/tests.

### 3. `swarm` mode становится не настраиваемым public default

Секция `[app]` и поле `mode` исключаются из публичного конфига. Runtime продолжает работать только в `swarm`, а это знание фиксируется в коде и spec без необходимости писать `mode = "swarm"` в каждом инстансе.

Почему так:
- других режимов больше нет;
- явное значение не несёт функциональной нагрузки.

Альтернативы:
- Сохранить `[app].mode` ради “явности”. Отклонено: это мнимая гибкость.

### 4. Gemini и logging defaults остаются кодовыми, а TOML — опциональным override

`[gemini]` и `[logging]` не удаляются полностью, но переходят в optional override mode. Минимальный `settings.toml` может не содержать их вовсе. В публичном примере остаются только поля, которые реально полезно менять между инстансами, например `model` и `temperature`; retry/backoff/jitter/timeout и fallback model живут в кодовых defaults.

Почему так:
- эти параметры важны, но редко меняются;
- сохраняется возможность тюнинга без расширения минимального конфига;
- change остаётся безопасным и локальным.

Альтернативы:
- Полностью убрать `[gemini]` из TOML. Отклонено: слишком жёстко ограничивает runtime tuning.
- Сохранить полный набор параметров в примере. Отклонено: не решает проблему перегруженности.

### 5. Reload и runtime facade остаются совместимыми

`SettingsReloadWatcher` продолжит пересобирать `Settings` через тот же фасад. При reload runtime должен получать те же вычисленные поля (`db_path`, `prompts_dir`, `topics_path`, `bot_profiles_dir`, `gemini_*`, `log_level`), даже если их источник теперь чаще кодовый default, а не TOML.

Почему так:
- снижает blast radius;
- не требует переписывать `run.py` и runtime-инициализацию.

## Risks / Trade-offs

- Изменение публичного TOML-контракта может сломать существующие локальные `settings.toml` с секциями `[app]`, `[storage]` и `[prompts]` → Нужна явная миграция в docs и в spec delta с breaking change.
- Сохранение скрытых override-механизмов для тестов и совместимости оставляет часть старой сложности внутри `Settings` → Допустимо, потому что пользовательский контракт при этом упрощается.
- Если слишком агрессивно урезать `[gemini]`, можно потерять полезные runtime knobs для диагностики → Сохраняем optional override section, но сокращаем пример и recommended contract.
- Если default `config/settings.toml` будет не синхронизирован с README/tests, появится новая путаница → Нужно обновить docs, `.env.example` и конфигурационные тесты в одном change.
