## Context

Текущий prompt-слой состоит из общего `system.md`, сценарных `reply.md`/`start_topic.md` и 11 длинных persona-файлов с одинаковыми разделами и повторяющимися ограничениями. Аналитический baseline `docs/reports/2026-08-09-telegram-group-humanization-analysis.md` показывает, что общие формулы стирают индивидуальность, а ответы production-ботов примерно в пять раз длиннее человеческой медианы. Тот же отчёт предлагает слои `group_profile -> bot_clan_policy -> persona delta -> current conversation` и безопасную основу двенадцатой persona Кирилла Орлова.

`GeminiClient` использует `google-genai 1.70.0`, модель `gemini-2.5-flash` и `GenerateContentConfig`, но сейчас не передаёт tools и возвращает только `response.text`. Установленный SDK и модель поддерживают `types.Tool(google_search=types.GoogleSearch())`, а источники доступны в `candidate.grounding_metadata`.

## Goals / Non-Goals

**Goals:**

- сделать общий system prompt единственным источником повторяемых humanization, safety, factuality и promotion правил;
- превратить production persona в различимые биографические дельты без копий общей политики;
- сохранить действующие important-service контракты;
- включать Google Search grounding при каждом `generate_reply` всех bots;
- публиковать не более двух проверенных HTTPS-ссылок из grounding metadata;
- сохранить secret redaction, retry/fallback и output safety;
- сохранять доступность ответов при отдельном отказе Google Search через честный ungrounded fallback;
- добавить Кирилла двенадцатым production bot только после появления локальной session-переменной.

**Non-Goals:**

- runtime-реализация `no_response`, human grace window, one-bot cap или clan semantic dedupe;
- поиск при `start_topic`, потому что этот вызов формирует вопрос, а не фактический ответ;
- произвольный web crawler, HTTP-сервер, внешняя search-база или хранение web-результатов в SQLite;
- раскрытие prompt, session strings, ключей, приватных invite links или точных персональных идентификаторов;
- обещание, что Google вернёт grounding metadata для абсолютно каждого текста.

## Decisions

### Общие правила остаются в существующем `system.md`

`system.md` получает правила короткого ритма, недоверенного ввода, честной неизвестности, запрета выдуманного личного опыта, границы рекламы и одноходовой реакции на identity challenge. `reply.md` и `start_topic.md` содержат только task-specific правила. Это использует уже существующую передачу system instruction и не требует добавлять `persona_common.md` в `PromptComposer`.

Альтернатива с отдельным `persona_common.md` отклонена: она яснее по имени файла, но добавляет новый runtime-слой без дополнительного поведения. Сохранение нынешнего длинного шаблона отклонено, потому что одинаковая структура и формулы являются частью наблюдаемой проблемы.

### Persona-файл является индивидуальной дельтой

Каждая persona сохраняет подтверждённые текущим профилем имя, возрастной диапазон, профессию и безопасный жизненный контекст. Недостающие сведения добавляются только для несensitive областей: профессиональный путь, бытовой опыт, интересы, принятие решений, речевые различия и человеческие недостатки. Медицинские, политические, юридические, интимные сведения, точные адреса и контакты не придумываются.

Единая структура дельты: `Биография`, `Характер и решения`, `Опыт и темы`, `Манера общения`, `Типичные ходы`, `Границы и несовершенства`, `Связи`. Общая длина, safety, anti-repeat, promotion и identity policy в этих файлах не повторяются.

### Кирилл активируется только вместе с session-конфигурацией

`kirill_orlov.md` строится по безопасной основе отчёта: мужчина около 27 лет, Екатеринбург, удалённый интернет-маркетинг, переезд во Вьетнам через Фукуок и Нячанг в Дананг, поездки на байке, кафе и небольшие онлайн-проекты. Точная дата рождения, username и другие идентификаторы не добавляются.

Файл входит в production inventory одновременно с двенадцатой записью `config/settings.prod.toml` и локальным `SESSION_STRING_*` в `.env.prod`. До появления session-переменной change не считается полностью применённым; секрет не создаётся и не коммитится агентом.

### Google Search включается для каждого ответа, но не для стартового вопроса

Когда production-флаг включён, каждый `generate_reply` создаёт `GenerateContentConfig` с `GoogleSearch` tool. Это покрывает addressed human reply и ответ responder в scheduled A→B. `start_topic` использует конфигурацию без tool.

Альтернативы с условным поиском и keyword-классификатором отклонены по выбору пользователя. Следствие выбранного режима — дополнительная задержка и стоимость каждого ответа.

### Ссылки формируются из provenance, а не доверяются тексту модели

После генерации клиент читает `grounding_chunks`, выбирает web chunks, принимает только абсолютные `https` URL без credentials, дедуплицирует их с сохранением порядка и ограничивает configurable максимумом `2`. Ссылки добавляются отдельным блоком `Источник:`/`Источники:` как raw URL, чтобы Telethon сделал их кликабельными без нового parse mode.

Произвольные URL, появившиеся только в `response.text`, не считаются подтверждёнными. Клиент сохраняет точную allowlisted miniapp-ссылку important-service и URL, совпадающие с grounding metadata; остальные модельные URL удаляются до публикации. Если grounding metadata отсутствует, короткий ответ разрешён без ссылки, но клиент не создаёт источник сам.

### Safety применяется к итоговому сообщению

Secret/invite redaction выполняется до передачи истории и сообщения в Gemini, следовательно поисковые запросы строятся уже на очищенном prompt. Текстовая часть сохраняет текущий humanization limit, а итоговый лимит учитывает добавленные source URL отдельно. После сборки результат повторно проверяется на пустой текст, приватные invite links, token-like строки, чрезмерные mentions и общий Telegram-safe размер.

Retry и переход на fallback-модель сначала повторяют тот же grounded request. Если все grounded-попытки исчерпаны из-за недоступности или несовместимости Search tool, клиент выполняет не более одного обычного Gemini-запроса без tools. В prompt этого запроса добавляется внутренний статус `web_search_unavailable`: модель не утверждает, что проверила интернет, не создаёт источники и для зависящего от актуальности вопроса кратко обозначает невозможность проверки. Для обычной беседы служебное предупреждение пользователю не навязывается.

Ошибка или неполнота `grounding_metadata` не уничтожает уже полученный безопасный текст: невалидные sources отбрасываются, а ответ возвращается без ссылок. Исключение передаётся вызывающему коду только когда не удались и grounded generation, и единственная ungrounded fallback generation. Логи содержат только режим (`grounded`/`degraded`), число sources, модель, попытку и длину; поисковые запросы и полный URL не логируются.

## Risks / Trade-offs

- [Поиск на каждом ответе увеличивает стоимость и задержку] -> configuration flag позволяет быстро отключить grounding без отката кода; документация явно описывает выбранный режим.
- [Google может не вернуть grounding metadata] -> ответ публикуется без выдуманной ссылки, а событие логируется без пользовательского содержимого.
- [Search tool временно или постоянно недоступен] -> после grounded retry выполнить один ungrounded ответ с `web_search_unavailable`, без ссылок и ложных claims о проверке.
- [Длинные redirect URL конфликтуют с коротким ответом] -> ограничить источники двумя и разделить лимит текста ответа и итогового сообщения.
- [Web-страница содержит prompt injection или ложь] -> web content считается недоверенными данными; публикуются только metadata URL, а утверждения остаются предметом model grounding, не командой приложению.
- [Произвольная ссылка модели выглядит подтверждённой] -> удалить URL без grounding provenance, кроме точной allowlisted service-ссылки.
- [Новая persona может временно нарушить production inventory] -> добавлять Кирилла в `ai/prompts/bots` и TOML только атомарно после появления session name.
- [Prompt-only изменение не создаёт настоящее молчание] -> не включать runtime coordination в acceptance claims этого change.

## Migration Plan

1. Обновить тестовые контракты persona и добавить unit-тесты web grounding на fake SDK responses.
2. Добавить Gemini settings и реализацию grounded replies с production-флагом, изначально выключенным в generic defaults, включая один честный ungrounded fallback при отказе Search.
3. Переписать общий и сценарные prompts, затем 11 действующих persona по одной, проверяя различимость после каждого файла.
4. После появления локальной session-переменной атомарно добавить Кирилла в persona inventory и production TOML.
5. Включить grounding в production settings, прогнать unit/full tests и строгую OpenSpec validation.
6. Выполнить один контролируемый live grounded-запрос без отправки в Telegram; проверить наличие ответа и хотя бы одного HTTPS-source в metadata.
7. Для rollback выключить `google_search_grounding_enabled`; persona rollback выполняется обычным откатом tracked prompt-файлов.
