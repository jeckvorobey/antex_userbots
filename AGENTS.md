# tg_userbot — инструкции для Codex

## Назначение проекта

Telegram userbot на базе Telethon, который работает в режиме `swarm`:

- в одном процессе запущено несколько userbot-аккаунтов;
- каждый bot постоянно онлайн и слушает целевую группу;
- если пользователь делает `reply` на сообщение конкретного bot, отвечает только этот bot;
- orchestrator по расписанию запускает случайные `A -> B` обмены;
- все сообщения сохраняются в SQLite;
- persisted history используется для anti-repeat поведения, чтобы боты не задавали один и тот же вопрос каждый день;
- в ключевых потоках есть подробное логирование.
- Если проект использует OpenSpec, агент не должен сразу приступать к реализации новой функциональности. Сначала необходимо проверить, существует ли активный change. Если его нет — предложить создать его через openspec-propose или создать самостоятельно, если пользователь явно запросил реализацию.

## Технологии

| Компонент | Библиотека | Назначение |
|---|---|---|
| MTProto | `telethon` | Подключение к Telegram как user |
| AI | `google-generativeai` | Генерация ответов через Gemini |
| Scheduler | `apscheduler` | Планирование orchestrator tick |
| Database | `aiosqlite` | История сообщений и persisted state |
| Config | `pydantic-settings` | Секреты из `.env`, несекретные настройки из TOML |
| Testing | `pytest`, `pytest-asyncio` | TDD и async unit/integration tests |
| Python | `3.11+` | Целевая версия |

## Поток данных

```text
Human reply в группе
  → reply_router.py
  → per-bot coordinator
  → prompt_composer.py
  → gemini.py
  → history.py
  → ответ адресованным bot

Scheduled tick
  → orchestrator.py
  → exchange_store.py (persisted anti-repeat state)
  → prompt_composer.py
  → gemini.py
  → history.py
  → A задаёт вопрос, B отвечает
```

## Правила разработки

1. Сначала изучай существующий код и тесты, затем меняй реализацию.
2. Предпочитай TDD: тест до реализации, затем минимальное изменение кода.
3. Не завязывай тесты на внешние сервисы:
   - Gemini API мокировать;
   - SQLite подменять на `":memory:"`;
   - Telethon-клиенты подменять fake/stub-объектами.
4. Для async-логики использовать только асинхронные интерфейсы.
5. Комментарии и docstrings держать на русском языке.
6. Не хардкодить промты в коде.
7. Все новые ключевые ветки поведения должны сопровождаться логированием.
8. После каждого изменения поведения приложения, новой функции, изменения архитектуры или API автоматически обновляй:
   - `openspec/specs`;
   - `openspec/project.md`, если изменилась архитектура проекта;
   - связанную документацию проекта.
9. Документация всегда должна соответствовать текущему состоянию кода.

## OpenSpec Workflow

Для новых функций, крупных изменений, изменений архитектуры, API, БД, формата данных или публичного поведения используй OpenSpec-процесс:

1. Новые функции и крупные изменения начинай через `openspec-propose`.
2. Если задача требует анализа архитектуры, затрагивает несколько подсистем или есть несколько вариантов реализации, сначала используй `openspec-explore`.
3. После утверждения спецификации выполняй реализацию через `openspec-apply-change`.
4. После реализации обязательно выполняй `openspec-sync-specs`, чтобы изменения из delta specs попали в основные `openspec/specs`.
5. После успешного прохождения тестов архивируй завершённое изменение через `openspec-archive-change`.

Правила OpenSpec:
- перед созданием или применением change изучай текущие `openspec/specs`, активные `openspec/changes` и релевантную документацию проекта;
- для задач с архитектурой, БД или форматом данных сначала обновляй спецификацию OpenSpec, затем пиши код;
- если реализация выявила расхождение со спецификацией, сначала обнови artifacts change, затем продолжай код;
- если задача полностью завершена, change должен быть синхронизирован и архивирован;
- если задача не требует изменения поведения, архитектуры, API или формата данных, OpenSpec artifacts можно не создавать, но документацию проекта всё равно нужно поддерживать актуальной.

## Работа с Codex CLI и Hermes Agent

- Codex CLI и Hermes Agent должны придерживаться одинакового workflow разработки.
- Перед внесением изменений сначала изучай существующий код, тесты и документацию OpenSpec.
- Не выполняй скрытых рефакторингов, не относящихся к задаче.
- Не меняй публичное поведение приложения без явного требования.
- Предпочитай небольшие безопасные изменения вместо крупных переписываний.
- При неоднозначностях сначала задавай уточняющие вопросы либо используй режим исследования `openspec-explore`.
- Если задача затрагивает архитектуру, БД или формат данных, сначала обновляй спецификацию OpenSpec, затем пиши код.

## Ограничения

- `async` везде для БД и сетевых операций;
- только `aiosqlite`, без синхронного SQLite API;
- без FastAPI и HTTP-сервера;
- только SQLite, без PostgreSQL и Redis;
- persona загружать строго из `persona_file` в конфиге;
- все сообщения сохранять в БД;
- `SESSION_STRING_*` не логировать и не коммитить.

## Рабочие команды

- Установка зависимостей: `uv sync`
- Запуск тестов: `uv run pytest`
- Проверка сбора тестов: `uv run pytest --collect-only`
- Локальный запуск: `uv run python run.py`

## Checklist завершения задачи

Перед тем как считать задачу завершённой, агент обязан проверить:

- обновлены или добавлены тесты, если задача меняла поведение или добавляла функциональность;
- проект успешно проходит релевантное тестирование;
- документация обновлена и соответствует текущему состоянию кода;
- OpenSpec синхронизирован через `openspec-sync-specs`, если задача требовала OpenSpec change;
- change архивирован через `openspec-archive-change`, если задача полностью завершена;
- в финальном отчёте перечислено:
  - какие файлы изменены;
  - что именно реализовано;
  - чем подтверждена корректность реализации.
