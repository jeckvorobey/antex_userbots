## Context

`SwarmManager._start_single_bot()` корректно очищает частично запущенный replacement-клиент, но вместе с ним удаляет единственную запись `clients[bot_id]`. Следующая reconnect-попытка безусловно останавливает эту запись и падает с `KeyError`. В `run._run_swarm_mode()` scheduler callback замыкает Telegram-клиент, выбранный при старте, хотя runtime-disable меняет активный пул.

## Goals / Non-Goals

**Goals:**

- Позволить supervisor повторять reconnect после любого числа временных startup-ошибок.
- Исключить обращение scheduler к остановленному клиенту при разрешении групп.
- Безопасно пропускать tick, если активного клиента временно нет.

**Non-Goals:**

- Не менять backoff, global quarantine и критерии активности бота.
- Не менять формат конфигурации, Telegram membership flow или параллелизм scheduler.

## Decisions

1. Reconnect будет извлекать предыдущий клиент через `dict.get()` и останавливать его только при наличии. Очистка неуспешного replacement остаётся в `_start_single_bot()`, а следующая попытка создаёт новый клиент через существующую factory. Альтернатива — сохранять остановленный объект в словаре — отвергнута, поскольку это поддерживает ложное runtime-состояние.
2. Scheduler callback будет выбирать первый актуальный `active_bot_id` непосредственно перед обработкой групп. При пустом active pool callback вернёт `False` с безопасным структурированным логом. Альтернатива — обновлять замкнутую ссылку при каждом disable/reconnect — сильнее связывает manager и scheduler.
3. Regression-тесты проверят наблюдаемое поведение: третий клиент успешно стартует после ошибки второго, а tick разрешает группу только через оставшийся активный клиент.

## Risks / Trade-offs

- [Активный пул может измениться во время tick] → Выбранный клиент фиксируется только на текущий последовательный tick; send-path всё равно проверяет доступность через manager.
- [Повторный stop одного клиента] → `dict.get()` и очистка replacement исключают обязательное наличие объекта, сохраняя идемпотентность повторной попытки.
