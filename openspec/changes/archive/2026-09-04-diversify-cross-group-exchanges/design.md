## Context

`SwarmOrchestrator._build_exchange_decision` и `_build_important_service_decision_if_due` вызывают `random.sample` после локального cooldown. Все запросы recent history передают group scope. `_next_important_service_scenario` начинает каждую новую группу с первого элемента. В `run.py` группы уже обрабатываются последовательно с ротацией первой группы, используют общий `ExchangeStore`, но при выборе не видят планы друг друга.

Независимая выборка допускает совпадение: `random.Random(5)` дважды выбирает `[2, 3]` из четырёх участников. Локальный probe существующего orchestrator подтвердил одинаковый `exchange_rub` в двух новых группах. Это воспроизведение поведения кода, а не утверждение о seed или конфигурации развёрнутого экземпляра.

## Goals / Non-Goals

**Goals:** разные пары и по возможности участники между группами, использование всего доступного roster, разнообразие стартовых сценариев/обычных тем, устойчивость при рестарте и маленьком пуле.

**Non-Goals:** изменение persona, маркировки AI-аккаунтов, service-контакта, cadence N+3, временных окон, human gates, addressed replies, LLM-провайдера или production-конфигурации. Абсолютная семантическая уникальность текста не гарантируется.

## Decisions

### 1. Общая сводка поверх существующих exchange-записей

Добавить отдельный async read API в `ExchangeStore`, возвращающий только group identity, participant ids, topic key, scenario key, статус и lifecycle timestamps за скользящие 24 часа относительно переданного `now` (UTC). Группы сопоставлять по реальному `group_chat_id`; legacy запись без chat id допускает сравнение по `group_id`, запись без обоих идентификаторов не участвует в межгрупповых предпочтениях.

Выборку ограничить `last_activity_at >= now - 24h`. `planned` резервирует обоих участников, тему и сценарий; `started` учитывает опубликованного инициатора и зарезервированного responder. Терминальные записи учитывают только действительно опубликованные роли по message ids; skipped до первого сообщения не оставляет резерва. Одноходовый completed exchange не приписывает участие неотправленному responder. При чтении для замены исключать сам заменяемый exchange.

Локальные методы cooldown и истории сообщений сохраняют прежний group scope и семантику фактической публикации. Общая сводка не переносит тексты сообщений между группами. Новую таблицу и замену существующего направленного `pair_key` не вводить; для сравнения пары использовать отсортированные два bot id. Проверить существующие индексы; если необходим индекс `last_activity_at`, добавить идемпотентно с тестом legacy схемы.

### 2. Ранжирование допустимых пар

Сначала исключить disabled/unavailable ботов по текущим runtime-проверкам. Для оставшихся различных A/B минимизировать лексикографический score:

1. Число использований/резервов неупорядоченной пары в других группах за 24 часа.
2. Минимальное ослабление локального cooldown prefix, нужное для допуска обоих участников.
3. Сумма использований/резервов обоих участников в других группах.
4. Сумма их использований/резервов во всех группах.
5. Сумма использований A как инициатора и B как responder во всех группах.

Среди одинаковых score выбирать случайно через подменяемый RNG. Так межгрупповой дубль не навязывается локальным cooldown; при отсутствии конфликта действующее исключение последних четырёх сохраняется. Это предпочтения с измеримым fallback, а не вечный запрет: при двух доступных ботах обмен продолжается.

Вычисление cooldown-кандидатов остаётся линейным согласно `efficient-bot-candidate-selection`. Ранжирование пар — отдельный этап, O(B²), без SQL на каждую пару: 182 направленные пары при 14 ботах. Агрегаты общей сводки строятся один раз на решение; чистое ранжирование и агрегаты размещаются в `userbot/exchange_diversity.py`, интеграция — в orchestrator. Регрессии общего store/runtime размещаются в `tests/test_cross_group_diversity.py`.

Альтернативы: независимый RNG не даёт гарантии разнообразия; постоянное закрепление ботов за группами сокращает roster и не даёт ротации. Выбрано ранжирование с общей persisted историей.

### 3. Выбор и резервирование согласованы

Общий для orchestrators одного runtime planning lock охватывает чтение сводки, проверку существующего group/window exchange, выбор и сохранение `planned` записи. Сам lock размещается на общем coordinator либо `ExchangeStore`, отдельно от SQLite transaction lock. Внутри него не вызывать Telegram или LLM, не ждать due time. Каждый следующий план видит уже сохранённый предыдущий.

При ошибке до commit резерва нет; после commit рестарт читает существующий план и сохраняет его пару, тему и due time. Замена ещё не отправленного участника использует ту же координацию и ранжирование с фиксированным counterpart, исключая failed bot и текущую запись из сводки. Уже отправленные сообщения повторно не отправлять. Несколько процессов, пишущих в одну runtime-БД, не входят в существующую архитектуру и этим изменением не поддерживаются.

### 4. Сценарии и темы

Для группы без валидного последнего service-сценария выбрать случайно среди ключей с наименьшим числом резервов/публикаций в других группах за 24 часа. При трёх одновременно новых группах и четырёх сценариях их первые сценарии различаются. Затем сохранить прежний циклический порядок относительно выбранной стартовой позиции; старые группы продолжают свой persisted цикл. Если все варианты использованы, допускается наименее частый. Cadence N+3 и responder requirement сохраняются.

Обычные темы сначала фильтровать текущим локальным anti-repeat; внутри получившегося пула предпочитать минимальное число выборов темы другими группами за 24 часа, случайно разрешая равенства. Если локальных свежих тем нет — применять этот же выбор ко всему пулу. Пустой список selector сохраняет действующий fallback.

Это обеспечивает разнообразие тем и стартовых фаз, но не вводит отдельный semantic-dedupe сервис и не меняет формулировки промтов.

### 5. Логи и проверка

Логировать group id, bot ids, уровень ослабления и численные количества кандидатов/конфликтов. Не логировать session material, private invite, полный текст сообщений или исключений Telegram.

Детерминированные тесты проверяют фактические планы/публикации с общей SQLite `:memory:` и fake Telegram/LLM: 4/2, 14/3, 4/5, только два доступных бота, cooldown-конфликт, роли, регулярные и service exchanges, конкурентное планирование, замена, истечение 24 часов и повторное создание orchestrators поверх сохранённой БД. Отдельно сохранить действующий тест линейного выбора кандидатов и group-scoped истории.

## Risks / Trade-offs

- Мало доступных аккаунтов → повтор допустим только после минимизации score и сопровождается логом; unavailable аккаунты не возвращаются в пул.
- Общая активность меняет локальный cooldown → приоритеты закреплены в delta spec, тест проверяет конфликт правил.
- Случайность может скрыть регрессию → проверки не зависят от вероятности, tie-break RNG подменяется.
- Разные стартовые фазы не исключают совпадений позже при разных расписаниях → гарантия различных service-сценариев касается начального выбора при доступных альтернативах; дальнейший цикл остаётся совместимым.
- Старые зависшие планы → предпочтения ограничены 24 часами и не блокируют scheduler навсегда.
- Резервы влияют на распределение до публикации → это отдельное понятие, не меняющее локальный published-only cooldown.

## Migration Plan

После утверждения: RED-тесты, реализация, релевантный и полный pytest, обновление README/project, sync specs, strict validation, archive. Существующие планы не переписывать. Новый алгоритм применяется к новым планам и необходимым заменам участников. Deploy и Git delivery требуют отдельного запроса. Откат к старому коду сохраняет читаемость существующих exchange-записей.
